## 2. CODE QUALITY ASSESSMENT

The code is small and generally readable. Controllers contain 13, 16, and 27 lines and delegate provider/persistence work. `Chat::Client`, `Chat::Broadcaster`, and the two tools have understandable responsibilities and names. The arithmetic parser uses explicit precedence and bounded recursion rather than eval (`app/services/chat/arithmetic.rb:25`). Tailwind is split by concern; Rails partials own the markup. There is no large method or class that alone dominates the implementation: the largest Ruby class is the 145-line store, and the Stimulus controller has 105 lines.

The main complexity is implicit coupling. `Chat::Store` combines Redis connection/transaction handling, a mutable string-keyed state schema, turn ownership, token accounting, recovery, and trimming. Controllers, services, and ERB all know that hash schema. `Store#read` can write recovery state (`app/services/chat/store.rb:19`), a side effect its name does not reveal. `Chat::Turn#call` combines reservation, streaming callbacks, title generation, commit, and exception cleanup (`app/services/chat/turn.rb:12`). These are manageable at this size but make lifecycle changes harder to reason about.

There is concrete duplication: allowed tool names occur in `client.rb:27` and `store.rb:49`; token framing/schema allowances are separately assembled in `store.rb:32`, `client.rb:52`, and `title_generator.rb:12`; conversation/sidebar rendering is issued both by `broadcaster.rb:7` and `app/views/messages/create.turbo_stream.erb:1`. Redis prefix/model/limit defaults also span application and deployment configuration. The explicit default mismatch for `FORCE_SSL` is listed below.

No clearly dead application feature was identified. `app/helpers/application_helper.rb` is empty scaffolding, and several configuration files retain irrelevant generator comments, including database guidance in `config/environments/test.rb:1` despite the absence of Active Record. `Arithmetic#term` has an unreachable case fallback under its current operator regex; the uncovered defensive branch is not a missing arithmetic feature. Broad rescues in `turn.rb:29`, `:48`, and `:62` protect the UI but also hide programmer errors and remove useful operational diagnostics.

The top three refactors I would prioritize are:

1. **Make the provider result and required tool set explicit.** Replace the boolean tool-intent result and loose string return with a small result contract carrying completion status and executed tools (`client.rb:18`, `tool_intent.rb:3`, `turn.rb:17`). Centralize the tool names. This would make the demonstrated wrong-tool and unfinished-stream cases enforceable at one boundary.
2. **Separate conversation policy from Redis transport.** Keep WATCH/MULTI in `Store`, but move state validation, lifecycle transitions, bounds, and shared token-estimation rules into a cohesive state/policy object (`store.rb:25`, `:53`, `:98`, `:138`; `token_usage.rb`). This would reduce string-key coupling and make corruption, retry, and budget invariants easier to test without duplicating formulas.
3. **Reduce whole-form replacement and define render ordering.** Consolidate the HTTP and broadcast reconciliation paths, preserve local drafts, and distinguish persistent conversation state from browser request state (`broadcaster.rb:7`, `create.turbo_stream.erb:1`, `chat_controller.js:77`). The purpose is to make multiple-tab and reconnect behavior testable, rather than merely splitting the JavaScript into more files.

## 4. KNOWN DEFECTS AND RISKS

### Confirmed defects

1. **Unfinished provider output can enter replayable history (G10).** `Chat::Client#reply` checks only whether returned text is nonempty (`app/services/chat/client.rb:37`). Probe P3 supplies HTTP 200 containing one SSE text delta with `finish_reason: null`, no terminal event, and no `[DONE]`. The real SDK returns that text; `Turn` saves two messages containing `Incomplete answer`, with `pending: null` and `error: null`. A clean premature upstream close is therefore indistinguishable from a successful exchange at the application boundary. Completion/truncation needs explicit validation before committing.

2. **Tool use is not enforced for the relevant task (G7).** `app/services/chat/client.rb:40` only checks `calls.zero?`; it never verifies which required tool ran. Probe P1 asks `What time is it?`, executes calculator for `2+2`, and accepts `It is noon UTC.` with tools `["calculator"]`. Probe P2 asks `Add two and two.` and accepts `Four.` with no tools because `ToolIntent.required?` returns false. The system instruction requests correct behavior but does not enforce it. Requests requiring both tools are also not checked for both executions.

3. **Invalid query IDs produce an HTTP 500.** Exact command: `curl -s -o /dev/null -w '%{http_code}\n' 'http://127.0.0.1:3000/?id=invalid'` → **500**. `ApplicationController#conversation_id` accepts query parameters (`app/controllers/application_controller.rb:10`), while the root route has no ID constraint. `Store#key` raises `ArgumentError` (`store.rb:83`), which the show action's `Chat::Error` rescue does not handle (`conversations_controller.rb:7`). Validate IDs before session assignment and return a controlled client error.

4. **Stored JSON is parsed but its shape is not validated.** Probe P4 writes `[]` to an isolated conversation key and `Chat::Store#read` raises **TypeError**. `app/services/chat/store.rb:121` catches syntax errors only; subsequent string-key access assumes a hash with valid fields. This requires corrupted or externally modified storage, not an ordinary prompt. It would escape the friendly storage-error handling. Validate the persisted schema before accessing it.

5. **The documented Compose SSL override is ignored.** `README.md:61` says to set `FORCE_SSL=true`, but `compose.yml:19` hardcodes `"false"`. `SECRET_KEY_BASE=self-review-placeholder FORCE_SSL=true docker compose config --format json` was parsed locally and its web environment still reported **FORCE_SSL=false**. Local HTTP works; the documented HTTPS deployment step does not enable Rails SSL enforcement through Compose.

The command `mise exec -- bundle exec ruby tmp/self_review_probes.rb` exits 0 and prints the P1–P4 observations above. Exit 0 means the probe completed; it does **not** mean those behaviors satisfy the goals. No real provider requests or changes to the running conversation store were made by the probes.

### Additional risks and limitations

- **Draft loss and stale UI updates — code-inspected, not browser-reproduced here.** Every state broadcast replaces the conversation content, including its empty composer (`broadcaster.rb:8`, `app/views/conversations/_content.html.erb:16`). Another tab's submission can replace an unsent draft; the JavaScript only captures a draft when that tab submits (`chat_controller.js:80`). State messages also carry no revision, so a delayed completed-state update from an older request can overwrite the display of a newer turn. Redis ownership checks protect stored history, not DOM ordering.
- **Subscription recovery has gaps — inferred from control flow.** Reconnection reloads only when the current form is already marked busy (`chat_controller.js:26`). A tab disconnected before another tab starts a turn can miss all broadcasts, reconnect with a nonbusy form, and stay stale. Initial subscription also does not resynchronize a pending-page snapshot (`:29` and the test at `test/javascript/chat_controller_test.mjs:75`); the timer eventually reloads it. These are not covered by the successful streaming tests.
- **Per-conversation bounds are not global admission control.** Anyone who can reach this intentionally unauthenticated demo can create new conversation IDs and start provider work. A fresh ID gets a fresh budget. Compose has ten Puma request threads (`compose.yml:12`); active turns hold them through generation/title work (`turn.rb:17`, `:46`). There is no application-wide request/spend limit or load-test evidence. Redis's 128 MiB noeviction cap bounds memory but can make all new writes fail when full.
- **Streaming persistence is expensive per chunk.** Each delta opens a Redis connection and rewrites the full conversation JSON in a WATCH/MULTI transaction (`store.rb:41`, `:88`, `:105`), with `appendfsync always` (`compose.yml:32`). This can amplify disk/network work under many small chunks. No throughput, disk-pressure, or OOM acceptance test was run.
- **TTL and turn deadlines are independently configurable.** Settings permit a 60-second TTL and up to a 180-second turn (`settings.rb:13`), while key expiration is refreshed only on writes (`store.rb:105`). A long interval without persisted text/tool activity can expire the entire key during an active turn, especially if the provider sends only keepalive/nontext chunks. This is a configuration/control-flow risk; the suite tests ordinary TTL expiry separately from active turns.
- **Title generation delays durable completion.** The first answer is committed only after title generation finishes or its ten-second timeout elapses (`turn.rb:24`, `:46`). A worker crash in that window leaves the visible answer pending, and recovery discards it. A title failure is never retried after the first exchange (`turn.rb:44`). Ordinary title failure preservation is tested; process death in this interval is not.
- **Operational visibility is limited.** Broad rescues map unrelated failures to fixed messages and discard final broadcast failures; RubyLLM logging is disabled (`config/initializers/ruby_llm.rb:7`). The `/up` health check does not check Redis or the provider (`config/routes.rb:2`, `Dockerfile:32`). Containers can appear healthy while chat is unusable. AOF and a persistent volume do not provide backups or host-loss recovery.
- **Security boundary is intentionally narrow.** Possession of a conversation URL grants access, and production host restrictions and CSP remain commented out (`config/environments/production.rb:53`, `config/initializers/content_security_policy.rb:7`). ERB escaping, CSRF defaults, localhost Compose binding, and secret filtering are present, but this is not evidence of safe unrestricted public deployment. Brakeman/bundle-audit results do not cover all of these runtime properties.
- **Token counts remain estimates.** They use bytes/4 plus allowances, not provider billing/tokenizer counts (`token_usage.rb:5`, `client.rb:52`). An admitted reply can overshoot the budget, and new IDs bypass the per-conversation total by design. Tool argument/nontext stream buffering inside the SDK is not subject to the application's text-byte cap. These limits should not be interpreted as a hard provider-cost or whole-process memory ceiling.
