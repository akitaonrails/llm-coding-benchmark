## 2. Code quality assessment

Overall the codebase is small (410 relevant lines per SimpleCov) with mostly single-purpose classes and names that say what things are (`ChatTurn`, `ConversationStore`, `TokenBudget`, `ConversationBroadcaster`). Layering is clean: controllers are thin (both under 25 lines), domain logic lives in POROs, all Turbo output funnels through one broadcaster. No dead files, no copy-paste duplication found; RuboCop (omakase) is clean.

Honest criticisms, with files:

- **`app/services/chat_turn.rb` is the god-object risk.** At 132 lines it orchestrates preflight, budget gating, chat construction, streaming, usage accounting (`usage_from`), persistence, and title generation. Each piece is small, but the class touches five collaborators and owns two distinct concerns (running the exchange vs. accounting for it). It is the file most likely to grow badly.
- **Blanket `rescue StandardError` conflates failure stages** (`chat_turn.rb:76-79`). An exception raised *after* `persist_exchange` succeeds (e.g. a broadcast failure in `finalize_message` or inside `generate_title`'s store update) shows the user "this turn was discarded" while the turn was in fact persisted. Correctness of the replayed payload is unaffected, but the UI can lie in that window.
- **Test seams live in production code.** `LlmChatFactory.builder=` / `.reset!` (`llm_chat_factory.rb:10-22`) and the `respond_to?(:before_tool_call)` guard (`chat_turn.rb:88`) exist only for tests/defensiveness. `ConversationBroadcaster`'s dual-type constructor (`conversation_broadcaster.rb:7-13`) accepts a raw string stream name that no production caller uses — SimpleCov confirms that branch is never hit outside tests.
- **Config duplication with drift risk:** the defaults table in `README.md:72-82` restates `ChatConfig` constants by hand; nothing keeps them in sync.
- **`Conversation#enforce_caps!` trims per-message, not per-exchange** (`conversation.rb:59-63`), so trimming can leave history starting with an assistant message — harmless to the provider but semantically odd.

Top 3 refactors with more time:

1. **Split `ChatTurn`** into the exchange runner and a post-exchange step (usage accounting + title kick-off), and narrow the rescue so post-persist failures don't render a false "discarded" message. This is the highest-value change because it fixes a real (if narrow) UI-truthfulness bug while shrinking the largest class.
2. **Move the LLM exchange off the request thread** (`messages_controller.rb:5-15` blocks a Puma thread for the entire provider stream). With 3 threads × 2 workers in the compose setup, 6 concurrent slow chats starve the app. Active Job is excluded by the brief, but a bounded thread-pool executor would do; the UI already works entirely over broadcasts, so the HTTP response could return immediately.
3. **Serialize turns per conversation server-side.** The store lock protects individual writes, but nothing prevents two overlapping `ChatTurn`s for the same conversation (double-submit, second tab) from interleaving history. A per-conversation "turn in progress" guard would close it.

## 4. Known defects and risks

1. **Request-thread blocking / capacity ceiling.** Each in-flight chat pins a Puma thread for the full provider stream (`messages_controller.rb:6-9`). The compose deployment has 2 workers × 3 threads: 6 concurrent chats make the app unresponsive, including `/up`. No app-level timeout is set on the provider call; it relies on ruby_llm/Faraday defaults.
2. **No server-side guard against concurrent turns on the same conversation.** Two overlapping submissions each replay the history they read at start; both persist, so messages interleave out of order and the second request's payload will not contain the first's still-in-flight exchange. The per-request exactly-once guarantee (G5) holds, but cross-request ordering is unguarded. The UI composer makes this hard to trigger (input clears on submit) but a second tab or scripted client can.
3. **Lock-file deletion race in `ConversationStore`.** `delete` (`conversation_store.rb:66-71`) unlinks the `.lock` file without holding it. A process still flocked on the unlinked inode and a new process creating a fresh lock file can both "hold the lock" simultaneously, breaking write atomicity for that conversation. Requires delete (TTL expiry on read, or "New chat") racing an update; unlikely but real.
4. **`flock` assumptions.** Correctness depends on the store directory being a local filesystem. On NFS or other network mounts, `flock` semantics degrade and the G6 guarantees silently weaken. The Docker named volume is local, so the shipped configuration is fine.
5. **Budget overshoot within a single turn.** `TokenBudget#exceeded?` is checked only before the call (`chat_turn.rb:48`); a conversation at 49 999/50 000 tokens can still fire a turn of arbitrary size (`max_tokens` is not constrained). Budget is a between-turns gate, not a hard cap.
6. **Post-persist failures render a false "discarded" message** (see §2). Window is small (between store write and broadcast) but the message is factually wrong when it happens.
7. **Expired-conversation sweep is opportunistic.** `purge_expired!` runs only on `create` (`conversation_store.rb:28`), so expired JSON files linger until the next new conversation (they are also deleted on read). Disk growth is bounded by traffic pattern, not by time; there is no background sweeper. The `create`-time sweep is also O(all conversations) per new chat.
8. **Untested production LLM wiring** (§3): `LlmChatFactory::DEFAULT_BUILDER` is only proven by phase 2's live probes, not by the suite. A regression there ships with green tests.
9. **Per-token Redis fan-out.** Every streamed chunk is one `broadcast_append_to` → one Redis publish → one Cable message per subscriber. Fine for a demo; at scale this is chatty and has no batching/backpressure.
10. **Calculator bignum edge.** `ArithmeticEvaluator` caps expression length at 200 chars but not operand magnitude: `9…9 * 9…9` with ~90-digit operands is cheap, but chained multiplications of large integers can produce very large bignums; cost is bounded by the 200-char expression (a handful of multiplications), so this is a theoretical rather than practical DoS.
11. **Session-cookie-scoped access only** (accepted per G14): anyone who obtains the signed session cookie can read/extend that conversation. Stream names are signed by Turbo, so cross-conversation snooping via Cable is not possible without the page-embedded signed stream token.
