# v4.2 — Concurrency / Capacity Report (how many coders can one pod serve?)

**Question:** how many concurrent coding-shaped users can a datacenter pod comfortably serve, and how does that scale across hardware? Two flagship open-weight coders of **equal v4 quality (both 92.5/A)** — DeepSeek V4.1 Flash (heavier MoE) and GLM 5.3 Flash (lighter) — ramped on two pods, served **matched-precision FP8, TP=4**, identical coding-shaped load.

## Method (SLO-goodput)
- Load: `vllm bench serve`, random coding-shaped prompts — **input 8000 / output 800 tokens**, range 0.6 — run **on the pod against `localhost:8000`** so the tunnel is never the bottleneck.
- Ramp: concurrency **N = 1,2,4,8,16,24,32,48,64,96,128,192,256**.
- **SLO:** TTFT ≤ 2000 ms **and** TPOT ≤ 20 ms (≥ 50 tok/s/stream). **Comfortable-N = the max N where per-request goodput ≥ 95%** (fraction of requests meeting *both* bounds). This is the authoritative gate; the looser "median-latency" N is reported alongside for reference because it ignores the p99 queueing tail.
- All runs verified `completed > 0, failed == 0` on every level.

## Headline

| Run | Hardware | Precision | Single-stream | **Comfortable-N** | Median-gate N | Peak aggregate | Bottleneck |
|---|---|---|---|---|---|---|---|
| DeepSeek V4.1 Flash | **4×B300** | FP8 | 177 tok/s | **32** | 48 | 2778 tok/s | compute (KV 0.4%) |
| DeepSeek V4.1 Flash | **4×H200** | FP8 | 137 tok/s | **8** | 16 | 2506 tok/s | compute (KV 14%) |
| GLM 5.3 Flash | **4×H200** | FP8 | 175 tok/s | **8** | 16 | 1930 tok/s | **KV (97%)** |

> **Note on scope:** GLM 5.3 Flash could **not** be ramped on the B300 — the B300 pod went unreachable during an NVFP4 autotune and was then closed (balance), so the B300 half is DeepSeek-only. The H200 pod was provisioned afterward to continue; **it is a different machine**, so B300↔H200 numbers are a hardware comparison, not the same box.

## Finding 1 — hardware scaling (same model, same TP=4, same FP8): B300 serves **4× more** comfortable coders
DeepSeek V4.1 Flash: **32 comfortable users on 4×B300 → 8 on 4×H200.** The driver is **prefill / time-to-first-token**, not decode and not memory:
- Decode (TPOT) and aggregate throughput hold up on both — the H200 still pushes 2506 tok/s raw at N=256 and never saturates compute.
- But the **p99 TTFT wall** hits ~4× sooner on H200: p99 TTFT is 1173 ms at N=16 on B300 vs **3192 ms on H200**, and on H200 it explodes to 51 s by N=256. Concurrent prefills queue far harder on the smaller/older box.
- **Raw throughput ≠ interactive capacity:** the H200 can emit 2506 tok/s aggregate but only ~8 users get an *interactive* experience — the rest are stuck in the prefill queue.

| N | B300 TTFT p50/p99 | B300 goodput% | H200 TTFT p50/p99 | H200 goodput% |
|---|---|---|---|---|
| 8  | 196 / 643 ms  | 100  | 391 / 1438 ms  | 100 |
| 16 | 184 / 1173 ms | 100  | 406 / 3192 ms  | 92.7 |
| 24 | 190 / 1727 ms | 100  | 422 / 5069 ms  | 20.1 |
| 32 | 194 / 2231 ms | 97.4 | 422 / 6577 ms  | 8.3 |
| 48 | 216 / 3111 ms | 92.0 | 472 / 8740 ms  | 4.2 |

## Finding 2 — heavy vs light on the SAME H200: both land at **8**, for opposite reasons
At equal 92.5 quality and matched FP8, the **lighter** GLM does **not** serve more concurrent users than the heavier DeepSeek — both comfortable at **N=8** — but the bottleneck differs:

- **DeepSeek V4.1 Flash is compute-bound.** Its MLA KV (`fp8_ds_mla`) is tiny — 8.25 M-token pool, peak **14%** KV util — so it keeps scaling aggregate throughput (**2506 tok/s** peak) and never hits a KV wall; the ceiling is prefill compute.
- **GLM 5.3 Flash is KV-bound.** The Glm5Next (Mamba-hybrid) KV budget is smaller (3.65 M tokens) and saturates — peak **97%** KV util — so its aggregate **plateaus at a saturation knee (N≈192, 1930 tok/s)** even though its single-stream decode is *faster* than DeepSeek (175 vs 137 tok/s).
- **Takeaway:** "lighter weights" did not buy more concurrent coders here. On this box the heavy MoE's efficient MLA KV let it push ~30% more aggregate throughput than the lighter model, whose KV footprint capped it first. Pick the serving model by its **KV architecture**, not just parameter count.

| N | DeepSeek agg / good% / KV | GLM agg / good% / KV |
|---|---|---|
| 8   | 626 / 100 / —     | 618 / 100 / — |
| 16  | 867 / 92.7 / —    | 768 / 51.0 / — |
| 128 | 2121 / 0 / —      | 1694 / 0.1 / — |
| 256 | 2506 / 0 / 14% pk | 1930 / 0 / **97% pk** |

*(GLM low-N goodput is TTFT-noisy — 83% @ N=1, 79% @ N=4 from first-token variance — but holds 100% at N=2 and N=8 and breaks hard at N=16, so comfortable-N=8 stands.)*

## Cost per comfortable user
Firm result = comfortable-N and tok/s above. Cost/comfortable-user = **(pod $/hr) ÷ comfortable-N** — plug in the *actual* RunPod rate for each pod (rates not re-verified here; do not trust placeholders):
- 4×B300 @ the campaign's **$36/hr** → DeepSeek **$1.13/comfortable-user/hr** (32 users).
- 4×H200 @ `$R/hr` → **$R/8** per comfortable user.
- **Counterintuitive implication to verify with real rates:** because the B300 serves 4× the comfortable users, it can be *cheaper per comfortable coder* than the H200 even though its hourly rate is higher — the H200 only wins on $/user if its rate is below ~$4.5/hr (= $36 ÷ 8). Confirm against the live RunPod pricing before quoting.

## Caveats
- **Different machines** for the B300 and H200 halves (B300 closed mid-test); not the same box.
- **Matched FP8** precision on all three runs (DeepSeek's working serve used UE8M0 block-scaled **FP8 DeepGEMM**, not the FP4/HUMMING fallback that appeared only in the pre-fix failed loads).
- GLM **B300** data is **absent** (never ramped before the pod closed).
- DeepSeek's saturation knee was **not reached even at N=256** on either pod (compute-bound, aggregate still climbing) — the comfortable-N is SLO-bound (TTFT), not throughput-bound.
- GLM served from `zai-org/GLM-5.3-Flash` (native FP8); the B300 build was `RedHatAI/...-NVFP4` (Blackwell-only).

## Serving hurdles (H200)
Hopper was **not** fully plug-and-play for these models — see [`docs/hardware-serving-playbook.md`](hardware-serving-playbook.md) for the full writeup. Summary: `pip install vllm` resolver-thrashed → **uv**; DeepSeek's FP8 **DeepGEMM + FlashInfer** JIT needed a 4-fix cu13 chain (NVRTC lib path; nvcc ≥12.9 → bundled **cu13 nvcc 13.4**; cccl **CTK-compat-check bypass** shim; FlashInfer **`-lcudart`** symlinks); and GLM OOM'd on model-swap until DeepSeek's orphaned TP workers were killed by PID. All infrastructure, none model-quality.
